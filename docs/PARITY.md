# Reference plugin functional parity

Source of truth for "does the Umbraco package do what the reference plugin (Blue Billywig's existing CMS plugin, version 2.0.5) does". Rows come from the plugin's own code: AJAX actions, REST routes, blocks, hooks, settings, admin scripts and `USER-GUIDE.md`.

## What counts as proven

A row is **Proven** only when all of these hold:

1. The Umbraco behaviour exists and is named in the row.
2. **Evidence** points at something that ran: a passing test, or a check observed in the running site against the development publication, with the date. "The code looks right" is not evidence.
3. Editor-facing rows were used through the backoffice UI, not only through the API.
4. Behaviour that writes to SAPI was checked by reading the result back from SAPI, on clips this project created.

Client (TypeScript) behaviour is tested (Vitest, in Node without a DOM) only for its pure helpers, the two public scripts against a hand-written fake DOM, and the translation files; the Lit elements themselves have no automated tests. A row that rests only on a UI observation is a single observation, and the audit pass re-observes a sample.

Parity means the same outcome for the user. It doesn't mean the same UI: an Umbraco convention replaces the reference plugin's where one exists.

| Status | Meaning |
|---|---|
| Open | Not built or not yet proven |
| Partial | Built, but some of the row is unproven. The notes say which part |
| Proven | Meets the rules above |
| N/A | No equivalent applies on Umbraco. The notes give the reason and what replaces it |
| Blocked | Can't be proven in this environment. The notes say what is needed |

The goal is reached when no row is Open, Partial or Blocked, and an independent audit that didn't build the feature has checked the table against the plugin and the running site. An N/A needs a real reason: "hard to build" is not one.

## Accepted deviations

Decided by the owner on 2026-11-04 (extended 2026-11-05). They differ from the reference plugin on purpose and are not defects.

| Area | Reference plugin | This package | Reason |
|---|---|---|---|
| Gate default access | administrator, editor, author and subscriber allowed | nobody until member groups are chosen | fail closed |
| Gate message | HTML filtered to a safe subset | HTML-encoded text, with the validated, encoded login link appended for anonymous visitors when one is set | smaller attack surface |
| Gate shared secret | any length | at least 32 characters for new values; a configured value is held to the same rule and fails closed | a short HMAC secret is guessable |
| Subtitle delete | Author level | needs the destructive-action policy | consistent with other deletes |
| Library access levels | a capability per action | the section-level Library policy covers metadata, bulk status and folder, and call to action edits; changing a clip's content protection policy needs the Delete policy | Umbraco convention; the protection change is stricter than the reference because removing a protection exposes the clip |
| Protected clip with the gate off | transcript, chapters and JSON-LD still render | player only | would leak protected text |
| CTA removal | Author level | Author-level policy on a POST route with a confirm body, a reviewed exception in the authorization sweep | parity with the reference's capability, CSRF-hardened |
| CTA image use type | n/a | the creative is stored as `commercial` | bb.dev stored an editorial clip when a creative was requested |
| Lazy-load and force switches | per-entity filters (`_lazy_load_oembed`, `_oembed_channel`, `_shortcode`, `bluebillywig_enqueue_lazy_loader`) | global options only (`DisableLazyLoader`, `ForceLazyLoader`, `LazyLoadOEmbed`, `LazyLoadOEmbedChannel`, `LazyLoadComponent`), no per-entity filter | no hook equivalent per entity yet (X3, X4) |
| Embargo fields | the banner prints the stored ISO text without naming a zone | the editor's fields and the banner are labelled and shown in UTC | the platform stores UTC |
| Uninstall | options wiped on uninstall | a manual "Remove stored settings" action; values are emptied, rows stay | a NuGet package has no uninstall hook (S11) |
| Per-clip playout | stored on the clip in SAPI | stored locally in Umbraco's key-value table, applied at render (embed > library > site default) | SAPI has no such field (E9) |

The Base URL is not a deviation: the reference 2.0.5 has no base URL setting. The package's configuration-only `BaseUrl` is an addition, restricted to Blue Billywig hosts, so a settings user can't redirect the read-write credential. The publication name check is the reference's (S15) except that configured and stored values may have 2 characters; the page size cap is 200 as in the reference (parity).

## Known issues

Found in the 2026-11-05 browser round on HEAD 4e8fb98 and the install test of rc.1 the same day.

- (a) Library search for a full hyphenated term (for example `umbraco-poc-test-b1`) returned the unfiltered default list while its parts (`umbraco`, `poc`, `b1`) filtered. The package sends the term escaped as `q=umbraco\-poc\-test\-b1` and nothing else (the reference plugin escapes the same way); the cause is not confirmed against the platform and is documented in [USER-GUIDE.md](USER-GUIDE.md) as probable upstream behaviour. Workaround: search for one part.
- (d) Uploads ignore the chosen status on bb.dev (U3).
- (e) SAPI cannot set archived or clear an embargo on bb.dev (M1, M3, E24); a past marker stands in for the embargo.

## Fixed after rc.1, unreleased

Fixed in the working tree after `1.0.0-rc.1`, covered by unit tests; not yet observed in a browser.

- A refused settings save showed only "Bad Request": the backoffice's API interceptor replaces any error body that is not problem details. Every backoffice API refusal (status 400 and up, including the automatic model-validation 400) is now problem details with the sentence in `detail` and `error` (`[RefusalShape]` on `BlueBillywigControllerBase`), the settings dashboard reads it and suppresses the generic toast, and the API base URL preview stays empty until the publication is valid.
- Settings dashboard inputs, selects, toggles and the textarea had no accessible label (console warnings "needs a label"); all have one, and a Vitest check over the sources fails when one is added without.
- The video picker kept a stale "Embargo removed." after Remove or a change of video (was known issue b).
- Focus fell to the page body after a bulk Apply or Delete in the library; it now moves to the result (or error) region (was known issue c).
- `/video-sitemap.xml` answered 503 and logged a Warning on a site without credentials; it now answers 200 with an empty valid urlset (logged once at Information). A configured site whose SAPI is unreachable still answers 503.
